Cluster-level simulation
Each AZ contains named ESX hosts. Affinity rules automatically place VMs. The last host in each AZ stays empty and is labeled Reserved for maintenance. Its CPU and memory are excluded from N+1 capacity totals. A 10% ESX memory reserve is applied to NUMA estimates only. Host logical cores are calculated from socket topology; VM CPU counts correspond to vCPUs.

Region placement board

Move VMs between AZs. Host placement is automatic.

Rule details

When enabled, these limits apply across both Kubernetes clusters within each AZ:

  1. Etcd separation and split: At most one etcd VM per host across both Kubernetes clusters. A four-vCPU etcd VM is modeled as 2 vCPUs on each of exactly two NUMA nodes, with half its memory on each.
  2. Etcd allowance on every host: Reserve 2 physical-core equivalents per NUMA node, even without etcd. Also reserve half the largest configured etcd VM's memory per node so hosts remain eligible to receive it.
  3. Local placement: Each worker, master, and ingress VM must fit completely within one node's remaining CPU and usable memory. NUMA memory includes the 10% ESX overhead allowance. Worker counts follow resource fit; there is no separate per-host worker-count cap.
  4. Independent roles: Master and ingress VMs need no matching number, host partner, or shared NUMA node. Moving one VM to another AZ does not move another VM.
  5. Role separation: At most one master and one ingress from each Kubernetes cluster per ESX host. VMs from different Kubernetes clusters may share a host if resources fit.

Turning off: Redistributes VMs within their current AZs without etcd slots, role separation, or strict NUMA fit. The original best-effort NUMA estimate and capacity warnings remain available.

Turning on: Recalculates automatic host placement under these rules. VMs without a valid placement remain visible as unplaced; configured counts and sizes are retained.

These are simulation policies, not VMware configuration or guaranteed optimal packing. No VM is tied to a fixed ESX hostname. The last host in each AZ is always reserved for maintenance and receives no VMs, with rules on or off. This reservation is already included in N+1 capacity totals.

Assessment assumptions

Green: two or more destinations. Amber: exactly one. Red: none. Unplaced VMs are counted separately. With affinity enabled, checks use the model’s strict NUMA budgets, etcd split/reserves, and role separation. With affinity disabled, checks use logical host CPU and configured RAM limits; overcapacity is rejected for this assessment even though the placement board permits it. Destination NUMA allocation may be recomputed within that host; other VMs remain on their ESX hosts. Results are independent possibilities, not a plan to move all VMs simultaneously or evacuate a host. This is a planning estimate, not actual VMware compatibility, network/storage validation, or guaranteed live NUMA behavior.
